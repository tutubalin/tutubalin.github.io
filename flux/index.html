Part 1
Pure theory

Not one line of source code in this part. § 1Rectified flow in five minutes

A FLUX.2 image is not painted. It is developed — out of pure noise, by asking one network the same question over and over: which way is real? This chapter is that question. Everything in model.py exists to answer it, and once you can answer it yourself, the rest of this article is bookkeeping.

1.1 · The single idea

Take a real image and call it x₀. Take pure Gaussian noise and call it x₁. Now draw a straight line between them and put a dot somewhere on that line. The dot's position is described by one number, t:

xt = (1 − t)·x0 + t·x1 with t = 0 → clean image,   t = 1 → pure noise

That is the entire "forward process". There is no gradual noise schedule, no Markov chain, no β-parameters — just a line segment. The model's whole job is to learn the velocity: the direction and speed you would have to travel along that line. Formally it learns the vector field

v(xt, t) = dxtdt = x1 − x0

Notice what that means: the target the network is trained to predict is simply noise minus image. Not the noise, not the clean image — the difference. This is why FLUX.2 is called a flow model rather than a diffusion model: it is trained to integrate an ordinary differential equation along (approximately) straight paths — flow matching (Lipman et al., 2022) with rectified flows (Liu et al., 2022), both in §26.

1.2 · The walk: ask, move, ask again

Generation is a loop, and it is worth stating in words before any code appears (the code is in §23, where the loop lives). The sampler starts at pure noise and repeats, until it runs out of schedule:

  1. Ask. Hand the network the current image and the current time. It answers with a velocity — the direction and speed at which the image should move to become more real.
  2. Move. Step along that velocity by however much time is left in this interval. That is the pink arrow in FIG 1, and it is the only thing in the whole sampler that changes the image.
  3. Repeat with the next, smaller time — until the schedule runs out at t = 0, which is a real image, and the autoencoder turns it back into pixels.

Nothing else happens. No noise is injected on the way, no variance schedule is applied, no randomness survives the first step: it is a deterministic integration of an ordinary differential equation, and the same starting noise plus the same prompt gives the same picture every time.

💡 Two questions this walk always raises

Which of the two times does the network get — the start of the interval or the end? The start: the noisier one, the time the image in hand actually corresponds to. That is what an explicit Euler step means — look at the ground where you are standing, then walk. Looking at the destination instead would require already knowing it.

And how does the network know how big a step to take? It does not, and it never needs to. It is only ever asked a local question — "at this image and this time, which way, and how fast?" — while the sampler owns the plan, having computed every one of the times before the walk began. That division of labour is why one set of weights can serve a 4-step, an 8-step and a 50-step run unchanged. §23 shows the code that does it.

⚠ Gotcha · which direction is "forward"?

The convention here is t = 1 is noise and t = 0 is data — the opposite of what many diffusion tutorials use, where t counts up as noise is added. In this codebase get_schedule returns timesteps starting at 1.0 and ending at 0.0, and the Euler step moves down. Keep that in mind whenever you see a timestep value: big = noisy, small = clean.

1.3 · The timestep schedule is not uniform

If you split [1, 0] into 50 equal slices you waste steps in the easy middle of the trajectory and starve the hard part. Which part is hard? Empirically, the noisy end: deciding the global composition from near-pure noise is where most of the information is created, and it is also where the velocity field curves the most. So FLUX.2 warps the uniform grid through a shift function, taken from the Stable Diffusion 3 paper:

t′ = eμeμ + (1/t − 1)σ μ = f(number of tokens, number of steps), σ = 1

Two things to take from that formula, and neither is a number. The shift is deterministic: the same canvas size and the same step count always produce the same ladder, so there is no seed and nothing random in a run. § 2FLUX.2's structure — three models, one job

Before any of it can be explained, one thing has to be said clearly, because it decides what model.py is and is not: FLUX.2 is not one model. It is three, bolted together, and the file this article walks through is only the middle one. The other two exist for a single reason — the middle one cannot read a word, and it cannot see a pixel.

2.1 · What the transformer never sees

The middle box has no idea what a word is and no idea what a pixel is. Its inputs are, in full:

Everything else — the meaning of the prompt, the look of a photograph, the fact that the output is supposed to be a picture of a cat — has already been converted into arithmetic by the time this file sees it. That is worth internalising before reading a single line of code, because it explains two things that otherwise look like odd choices. The network needs no vocabulary and no image handling, so it has none. And its output is not an image either: it is 4 096 rows of 128 numbers describing which way to move, which the sampler adds to the canvas and the VAE eventually turns into pixels.

Because it runs once. § 3From prompt to tokens — a 24-billion-parameter reader

The transformer's text input is 512 rows of 15 360 numbers. Not one word, not one embedding, not a sentence vector: 512 rows, each of them 15 360 wide. This chapter is where those two strange numbers come from — and the answer is that FLUX.2 reads your prompt with a large language model, then taps it at three depths and glues the results together.

3.1 · A language model that is never asked to speak

FLUX.2's text encoder is a decoder-only LLM: Mistral-Small-3.2-24B for the dev model, Qwen3-8B and Qwen3-4B for the two klein checkpoints. It is loaded frozen, it is not fine-tuned, and it is not asked to generate a single token. The prompt goes in, the model runs one forward pass, and what comes out is not text — it is the model's internal state, the numbers it was carrying about your sentence while it read it.

That is a different job from the one a language model was trained for, and it is worth pausing on, because it explains the rest of this chapter. An LLM's final layer is optimised for one thing: predicting the next word. Its earlier layers are not. They hold the intermediate work — which words are near each other, what refers to what, what kind of sentence this is — and none of it was ever trained to be a description suitable for painting with. So FLUX.2 does not take the last layer. It takes three.

3.2 · Three depths, glued side by side

Three hidden layers are read out of the stack and concatenated along the feature axis — layers 10, 20 and 30 for Mistral, 9, 18 and 27 for Qwen3. Roughly the shallow third, the middle and the deep end: local and syntactic, then relational, then fully semantic. Each of those layers carries one vector per prompt token, and gluing three of them side by side makes each token three times as wide.

Reading mid-depth layers rather than only the last one is a trick with precedent — SD3 does something similar — and the reasoning is the one above: a next-word predictor's output layer is specialised for predicting words, and an image model wants everything the reader understood on the way to that prediction. inference The layer indices are in the source; the justification is not written down anywhere.

3.3 · 512 tokens, whatever you typed

The second strange number is a limit: MAX_LENGTH = 512. Prompts are tokenised and then padded or cut to exactly 512 tokens, so a three-word prompt and a paragraph both arrive as 512 rows. Two consequences, and both show up later in the arithmetic:

  • The text half of the sequence is a constant. Image tokens grow with resolution — 1 024 at 512², 4 096 at 1024², 16 384 at 2048² — while text tokens never move from 512. That is why quadrupling the canvas does not quite quadruple the work of attention (§23.2), and why reference images dominate the sequence so completely at small sizes (§22).
  • Padding rows are real rows. They are attended to like any other token; the network learns to ignore them. Nothing in model.py masks them out, because nothing needs to.
⚠ The word "token" means two different things in this article

A language-model token is a piece of a word — what the tokeniser counts, 512 of them. An image token is a 16 × 16 patch of the picture — what the VAE and the patchifier produce, 4 096 of them at 1024². They meet inside the transformer as rows of the same sequence, and from that point on the distinction is only in their position ids (§8). When this article says "tokens" without qualifying it, it means rows of the transformer's sequence.

Used later: §4 (the other kind of token, and how a picture becomes 4 096 of them), §15 (context_in_dim, the field that carries 15 360), §16.3 (MLPEmbedder, which narrows it to 6 144), §20.2 (where ctx and ctx_ids arrive).

§ 4From pixels to tokens: what the model actually eats

model.py has no convolutions and no image logic. It receives images that have already been flattened into a list of vectors. To understand its shapes you must know exactly how that flattening happens.

4.1 · Three stages of compression

Two of the three stages happen inside the VAE, in autoencoder.py's encode(): the convolutional 8× downsample to 32 channels, and the 2×2 patchify that folds four latent cells into one 128-number token. The third — flattening that 2-D grid of tokens into a plain sequence and attaching the position ids — is sampling.py's prc_img, run just before the model is called:

◇ Beginner · why bother with latents at all?

Attention costs grow with the square of the token count. A 1024×1024 image as raw pixels would be over a million tokens: 10¹² attention pairs per layer, utterly impossible. As 4096 tokens it is 21 million pairs — expensive but feasible on real hardware. The latent space is a compression scheme that throws away perceptually irrelevant detail (exact sub-pixel noise) while keeping everything a human would notice. One detail worth knowing, because it explains a shape you will see in autoencoder.py: the 128-channel latent is normalised by a running-statistics BatchNorm2d(128, affine=False, eps=1e-4) inside the autoencoder (autoencoder.py L293–325) — no per-channel scale/shift factors for the transformer to carry around.

4.2 · What the VAE is, and why the transformer never sees a pixel

The first arrow in that figure — the one labelled "VAE encoder, 8× per side" — does more work than any single part of model.py, and it is not in model.py at all. It is worth a few paragraphs, because everything downstream depends on it.

◇ An autoencoder, in one paragraph

Take two networks: an encoder that squeezes an image into a small code, and a decoder that tries to rebuild the image from that code alone. Train them together on millions of images, scoring them on how close the rebuild is to the original. The code cannot keep everything — it is far too small — so training forces it to keep what matters and discard what the eye forgives: exact noise in flat sky, the precise shape of a leaf's edge, the third decimal of a shadow. What survives is a compressed description of the picture: layout, colours, objects, texture. The "V" in VAE means the encoder emits a distribution rather than a point, and the code is sampled from it during training — which is what makes the space smooth enough to generate in.

Why go to all that trouble? Because of one property of attention that §6 will derive from scratch: its cost grows with the square of the number of rows. At 1024², working directly on pixels would mean 1 048 576 rows per image. Working in latents means 4 096.

if the transformer worked on…rows at 1024²attention pairsverdict

That is the whole reason latent diffusion exists: compress first, think in the compressed space, expand once at the end. FLUX.2's particular compression is a two-stage affair, both stages inside the autoencoder:

  • 8× per side from the convolutional encoder. Its channel multipliers are [1, 2, 4, 4], which means three rounds of halving the resolution — 2³ = 8 — ending at z_channels = 32. A 1024² image becomes a 128 × 128 grid of 32-number cells.
  • 2× per side from the patchify. A pure reshape, no arithmetic: every 2 × 2 group of cells is concatenated into one row of 4 × 32 = 128 numbers. The autoencoder literally spells this as an einops rearrangement with ps = [2, 2].

Two details of this VAE matter later, and both are the opposite of what "variational" suggests.

💡 Nothing is sampled at inference

The encoder produces a mean and a spread, and encode() keeps only the mean. Encoding a reference image is therefore deterministic — the same photo gives the same latents every time — which is one of the reasons the KV cache of §22 can be bit-exact rather than approximate. The latents are then passed through a fixed per-channel normalisation with running statistics (128 channels, no learned scale of its own), so the transformer always receives them in the same range regardless of what the picture depicted.

And the decoder runs exactly once, after the last step, turning 128 × 128 × 32 back into 1024 × 1024 × 3. It is the only place in the whole system where a pixel is ever produced. The transformer — all 32 billion parameters of it, all 833 lines of this article — lives entirely inside the compressed space, and never knows what a colour is.

4.4 · Reference images are just more tokens

For editing and multi-reference generation, reference images go through the same VAE encoder and the same patchify, and their tokens are simply appended to the sequence. Up to ten references are supported; to keep the cost sane the pipeline caps reference pixels at 1024² each when there are several, and 2024² when there is only one (sampling.py L56–58 spells it 2024**2, which is what upstream says — almost certainly a typo for 2048²). The only thing that distinguishes a reference token from a canvas token is its position id — which is the subject of §8.

§ 5One language — how 128 and 15 360 both become 6 144

The transformer has exactly one internal width. Whatever arrives — a patch of a photograph, a reference image, a piece of your sentence — has to be re-expressed as a row of 6 144 numbers before it can take part, and whatever leaves is 6 144 numbers too. Two matrices do the translating. They are the first thing Flux2.forward touches and among the simplest objects in the file, but nothing downstream makes sense until you have seen why they exist and what they cost.

5.2 · Widening and narrowing are the same operation

The two doors look opposite — one multiplies the width by 48, the other divides it by 2.5 — but they are the same kind of thing: a change of basis. Each output number is a learned weighted sum of the inputs, and nothing else happens.

💡 Why the doors are plain matrices, while the time door is an MLP

Compare them with the two doors that are still to come — the ones for the timestep and for the guidance value. Those are time_in and guidance_in, and each is two linear layers with a SiLU between them: 256 → 6 144 → 6 144, 39 321 600 parameters apiece. Why the difference? Because of what arrives. A prompt row has already been through a 24-billion-parameter language model and a patch row through a trained autoencoder — their meaning is computed, and all that is left is a change of basis, which one matrix does. A timestep arrives as a 256-number code produced by a fixed formula (§7 builds that code, §9 feeds it in) — numbers with no learned meaning in them yet. Something has to decide what "t = 0.62" means, and that something is the second layer. inference — the shapes are in the file; the reasoning about why one door needs depth and the other does not is not written down anywhere.

5.3 · Why 6 144, of all numbers

The corridor's width is not free. It has to divide evenly into attention heads, because a head is just a slice of the row: head_dim = hidden_size // num_heads. FLUX.2 keeps the slice size fixed at 128 across all three checkpoints and varies the number of slices instead:

A fixed head width means the part of the architecture that is most geometry-sensitive stays constant while the model is scaled: every head, in every checkpoint, is 128 numbers = 64 rotation planes, so the RoPE ladder of §8 has the same shape everywhere and the attention temperature 1/√128 never changes. Shrinking the model removes heads, not resolution within a head.

⚠ Two different 128s

They are unrelated and it is very easy to conflate them. in_channels = 128 is how many numbers one token carries into the network: 4 latent cells × 32 channels (§4). head_dim = 128 is how wide one attention head is inside the network: hidden_size ÷ num_heads. One describes the outside world, the other the corridor. They would still both be 128 if the other were 96.

5.4 · The exit door

After 56 blocks the rows are still 6 144 wide, and they are still not an image — they are the network's opinion about which way each token should move. Turning that back into latents takes one more projection, and it is the mirror of img_in: 6 144 → 128, again a single bias-free matrix.

The exit has one thing the entrance does not: its own modulation. final_layer normalises each row with a parameter-free LayerNorm, applies a shift and a scale derived from the same condition vector vec that steered all 56 blocks — a fourth, private set of dials — and only then projects down. There is no gate, because there is no residual stream left to add anything to: this is the last operation, so "contribute nothing" is not an option it needs.

What comes out is 4 096 rows of 128 numbers, which is folded back into a 128 × 128 × 32 latent grid and handed to the VAE decoder — the only component in the whole system that has ever seen a pixel (§4.2).

noise (B, 4096, 128) → img_in → (B, 4096, 6144)
prompt (B, 512, 15360) → txt_in → (B, 512, 6144)

drop the text rows → (B, 4096, 6144) → final_layer → (B, 4096, 128)

Every one of those arrows is either a matrix multiply or a reshape. Repeat the middle of that fifty times and you have generated an image.

§ 6Attention, from zero

Everything from here on is built from one operation: attention. Every paper mentions it; few explain it. We will build it from scratch using nothing but a dot product and one paragraph about softmax — and by the end you will know exactly what a query, a key and a value are, why scores are divided by √d, what a "head" is, and, crucially for everything that follows, what attention cannot see.

6.1 · The question every token must answer

A token on its own knows almost nothing. The canvas token at row 17, column 42 holds a small patch of half-finished image; whether that patch should become "fox ear" or "shadow on snow" depends on tokens far away from it — the word fox in the prompt, a patch of the reference image showing the actual animal. So at every layer of the network, every token needs to ask the same question:

Σ The question

"Everybody else — what do you have that I need?"

Attention is the machinery that answers this question for all tokens at once, in parallel, using nothing but matrix multiplications. It is a soft database lookup: instead of fetching one record, every token takes a weighted slice of everything.

6.2 · Three roles per token: query, key, value

Each token vector x is linearly projected into three new vectors — three roles in the lookup:

  • the query q — the question this token is asking: what I am looking for;
  • the key k — the advertisement this token broadcasts: what I have on offer;
  • the value v — the payload this token will actually hand over if it gets chosen: what I carry.

A conference is the right picture: your query is what you hope to find, someone's key is what their name badge says, their value is the folder under their arm. How well a question matches an advertisement is measured by the simplest thing available — the dot product q·k: large when the two vectors point the same way, near zero when they are unrelated, negative when they oppose. The three projections are learned matrices (in FLUX.2 they are fused into a single matmul — the SelfAttention bundle of §16.8); nothing about them is hand-designed.

6.3 · From scores to weights: divide by √d, then softmax

Raw dot products need two adjustments before they can be used as weights.

First, scale. A dot product of two d-dimensional vectors adds d terms, so its typical size grows like √d — with d = 128 (the width of one head's q and k in FLUX.2, §15) that is a factor of ~11 of pure size, carrying no information at all. Dividing every score by √d removes it and keeps the next step sane.

Second, softmax. Weights must be positive and sum to one, so that "taking a little of everyone" is a well-defined mix. Softmax does exactly that: exponentiate each score (now everything is positive, and bigger scores are amplified), then divide by the total:

wᵢ = esᵢΣⱼ esⱼ with sᵢ = q · kᵢ√d and the answer is out = Σ wᵢ · v

Because exponentiation is steep, a score that is merely a bit larger than the others can take most of the weight — softmax is a soft maximum: usually "mostly one, a little of the rest", never a hard cut. (Which entries are allowed to compete at all is a separate question — FLUX.2's mask — and gets its own section, §17.)

6.4 · Heads: many lookups in parallel

One lookup can encode one kind of relationship at a time — "looks like", "sits next to", "contradicts". Real language and real images need dozens of such relationships at once, so the feature width is sliced into H independent sub-lookups called heads: FLUX.2 [dev] splits its 6144 dimensions into 48 heads of 128 dimensions each (§15), and every head runs its own private copy of §6.3 on its own slice — its own q, k, v, its own scores, its own weights. The head outputs are concatenated back into one vector and mixed by a final projection. Nothing in the code coordinates the heads — the 48 slices are just 48 independent lookups that happen to be computed in one batched matmul — and what each head ends up specialising in is a property of the trained weights, not of this file.

Remember the number 128: it is head_dim, the width of one head's query and key — and therefore the size of everything in this section. It appears again in the norms (§16.7), in the rotation planes (§8) and in every parameter count in this article.

6.5 · What attention cannot see: order

Notice what is missing from all of the above: position. The weights depend only on the contents of the vectors. Shuffle the tokens and the weights shuffle with them — the set of outputs comes back identical, rearranged. Attention is a perfect lookup and a total amnesiac: left to itself it has no idea which patches are neighbours, which reference image a patch came from, or which word preceded which in your prompt.

Everything spatial and sequential must therefore be injected into q and k before the dot product is taken. That is precisely the job of the next section — and the reason FLUX.2's position system is worth a chapter of its own.

§ 7The frequency trick — how one number becomes a vector

The sampler hands the network a single float: t = 0.62. One number. And that number has to change the behaviour of 32 billion parameters, 56 blocks deep, in a way that is different at 0.62 than at 0.63. Fed in raw it could never do that. This chapter is the trick that fixes it — the same trick the next chapter uses for positions, and one of the oldest ideas in the transformer literature.

7.1 · Why one float is a terrible input

Everything a neural network does with a number begins by multiplying it. So imagine the naive version: t goes straight into a weight matrix. Every output is then a fixed multiple of t, and the network's entire response to the timestep is a straight line — it can only ever respond more or less, monotonically, in one direction. There is no way to say "at t = 0.9 do this and at t = 0.1 do that", because the only thing distinguishing those two inputs is a scale factor.

Worse, remember where the run actually spends its time (§1.3): most calls sit in a narrow band just below 1. The difference between t = 0.985 and t = 0.967 is 0.018 — after one multiplication that is a whisper, easily lost among activations that are orders of magnitude larger. A single float carries almost no signal for a network to grab hold of.

💡 The fix, stated in one sentence

Do not give the network the number. Give it many different readings of the same number — some that change fast, some that barely change at all — and let it learn which readings matter.

7.2 · Tell the time with many clocks

An analogue clock solves exactly this problem. If it had only an hour hand, 12:00 and 1:00 would be distinguishable but 12:00 and 12:05 would look identical — the hand moves too slowly to resolve small differences. Add a minute hand and the two readings are obvious. Add a second hand and even 12:00:00 and 12:00:01 differ. One quantity — the time of day — becomes three readings at three different speeds, and together they pin it down exactly.

The sinusoidal encoding is a clock wall. Each "hand" is a cosine (or sine) turning at its own rate, and the rates are spaced evenly on a logarithmic scale, so between the fastest and the slowest there is a hand for every scale of difference you might care about.

All this chapter needs about sine and cosine is one fact: cos θ and sin θ are the coordinates of a point on a circle of radius 1, at angle θ. As θ grows, the point goes round and round; the two coordinates oscillate smoothly between −1 and 1, a quarter turn out of phase with each other.

7.3 · The recipe, exactly

Σ From one float to 256 numbers

t′ = 1000 · t

ωi = exp(−ln(10000) · i / 128) = 10000−i/128 for i = 0 … 127

fingerprint = [ cos(t′·ω0) … cos(t′·ω127) , sin(t′·ω0) … sin(t′·ω127) ]

one float in → 256 numbers out, every one of them between −1 and 1 · no weights, no state, nothing learned

The rates run geometrically from ω₀ = 1 down to ω₁₂₇ ≈ 1.07 × 10⁻⁴ — four decades of speed, 128 rungs. Over the whole run, as t falls from 1 to 0:

  • the fastest channel completes 159 cycles. It is a blur, and that is its job: it distinguishes t = 0.6200 from t = 0.6201.
  • the slowest gets through 1.7 % of one cycle — it barely moves, and that is its job: it says which end of the run you are in, and it says it in a way that changes smoothly rather than jumping.
  • between them, every scale in between, each ten-ish times slower than the last.

Two properties follow, and they are the reason this encoding has outlived a decade of alternatives:

propertywhat it means herewhy it matters
smoothevery channel is a smooth function of t, so t = 0.620 and t = 0.621 give fingerprints that differ by a hairthe walk of §1.2 moves in small steps; the network's instructions must not lurch between them
unmistakablewith 128 rates present, no two times in [0, 1] give the same 256 numbersthe network can always tell which moment it is being asked about — that is the whole point
boundedall 256 values live in [−1, 1] regardless of ta well-scaled input to the next layer, with no channel dominating

And the × 1000? A scale convention. It makes the argument run from 0 to 1000 rather than 0 to 1, which puts the useful part of the frequency ladder where the cycles are. It is not a consequence of the schedule and it carries no meaning of its own.

7.4 · Why a cosine and a sine

128 rates would be enough to make the reading unique, so why does the encoding use 256 numbers — a cosine and a sine at every rate? Because a lone sinusoid is ambiguous about where it is in its cycle, and a pair is not.

There is a bonus, and it is the hinge to the next chapter. A point on a circle at angle θ, moved on by a fixed amount Δ, is the same point rotated — and a rotation is a 2 × 2 matrix acting on the pair (cos θ, sin θ). So "a shift in position" becomes "multiply by a small matrix", which is exactly what rotary position embedding does in §9 with four coordinates per token instead of one.

7.5 · What happens to the fingerprint next

The 256 numbers are fixed and meaningless on their own — a code, not an interpretation. Two more steps turn them into something the network can act on, and both are in Part 3:

  • A learned widening. A small two-layer network (256 → 6144 → 6144, §16.3) maps the code to a single condition vector. This is where meaning is learned: which patterns of fast and slow readings correspond to "still noise", "shapes forming", "finishing touches". Nothing before it has a single parameter.
  • A learned projection into dials. Three matrices turn that vector into the shift, scale and gate values that every block is modulated by (§15). The fingerprint never reaches a block; only the dials do.

So the full journey of one float is: multiply by 1000, read 128 clocks twice each, learn a meaning for the reading, project it into 15 dials, and let 56 blocks be re-tuned by them. The first two steps are this chapter, and they cost nothing at all.

⚠ The same trick, used twice in this file

timestep_embedding encodes one scalar — the time, and (for the dev model) the guidance value. rope in the next chapter encodes four integers per token — its position — with the identical frequency-ladder machinery, but keeps the result as 2 × 2 rotations instead of flattening it into a feature vector. Same idea, two different jobs: one tells the network when it is, the other tells it where each token sits.

Used later: §9 (positions, the same ladder as rotations), §16.1 (timestep_embedding, the eleven lines that implement this chapter), §16.3 (MLPEmbedder, the learned widening), §15 (what the dials do once they exist).

§ 8Position: the four-axis rotary embedding

§6 ended on attention's blind spot: a dot product cannot see order. Feed the same tokens shuffled and the scores shuffle with them — nothing in the mechanism knows which token came first, or which patch sits next to which. Everything spatial about an image, and everything sequential about a sentence, must be injected deliberately, into q and k, before attention runs. FLUX.2 does it with RoPE, extended to four axes at once.

8.1 · RoPE in one paragraph — and three pictures

Attention scores are dot products: score = ⟨q, k⟩. And a dot product is blind to order — shuffle the tokens and the scores shuffle with them, without ever changing value. Position therefore has to be baked into q and k themselves, and there are two classic ways to do that. You can add a position vector to each token — but then content and position occupy the same directions and the model must learn to untangle them. Or you can rotate each vector by an angle that depends on its position. That second idea is RoPE — Rotary Position Embedding (Su et al., 2021) — and it is the better choice for one beautiful reason: rotating a vector changes where it points without changing what it is.

R(p·ω) = [cos pω−sin pωsin pωcos pω] a 2×2 rotation matrix (rows: cos, −sin / sin, cos), applied to q and k in one plane

Two facts about rotations then do all the work. Rotations preserve length, so a rotated token keeps exactly the same "loudness" — position can never amplify or silence content. And rotations compose by adding angles: turn by a, then by b, and you have turned by a + b; the transpose of a rotation is simply the same rotation run backwards, Rᵀ = R(−θ). Feed those two facts into the attention score and the absolute positions cancel out of the equation:

⟨Rp q, Rp′ k⟩ = qᵀ Rpᵀ Rp′ k = qᵀ R(p′−p) k ← one rotation, by the gap
so the score depends on p′ − p and on the two tokens' content — never on where either one sits

That line is the whole trick, and it is worth reading twice. The model never tells attention "you are at position 4096"; it turns each vector by an angle proportional to 4096, and lets the difference of two turns carry the only information the score needs: how far apart these two tokens are. Zero learned parameters, no maximum sequence length, nothing to look up in a table.

One plane, though, would not be enough. A head pairs its 128 dimensions into 64 rotation planes. In FLUX.2 those planes come in four groups of 16 — one group per position axis (§8.2) — and within a group the planes run at speeds ωⱼ = θ^(−2j/32), j = 0…15: a geometric ladder from ω₀ = 1 (a full turn every 6.28 positions on that axis) down to ω₁₅ = 1/θ^(30/32) ≈ 0.0008 (barely moving at all). The score is the sum of 64 such contributions, one per plane: cos((p′−p)·ω + φ). A fast plane is a minute hand: exquisitely precise about small gaps, but it returns to the same angle every period, so gap 0 and gap 6.28 look identical to it — it aliases. A slow plane is an hour hand: never ambiguous, far too coarse to tell neighbours apart. Summed together, the ladder gives every gap its own fingerprint.

For an image model this property is not a luxury, it is the product. FLUX.2 has to accept resolutions it has never seen — anything from 512² up to 4 megapixels — and a purely relative position code extrapolates to new sequence lengths in a way that absolute position tables famously do not.

◆ Verified · the property holds in this exact implementation

I rotated a fixed query/key pair with apply_rope at several position pairs and measured the dot product. Pairs with the same gap give the same score, agreeing to within 1×10⁻⁶ — pure float32 round-off:

gap = 2 : (p=0, p=2) → 4.919082   (p=5, p=7) → 4.919081   (p=13, p=15) → 4.919082
gap = 3 : (p=0, p=3) → 6.703997   (p=5, p=8) → 6.703996

I also confirmed each produced matrix is a genuine rotation: RᵀR = I to 6×10⁻⁸ and det R = +1.000000, and that apply_rope leaves every vector's norm unchanged.

8.2 · How 64 rotations fill one head's 128 numbers

The paragraph above said "rotate the query and the key". This is what that means mechanically, because it is the part that is easiest to imagine wrongly: nothing is multiplied by a big matrix, and no dimension is ever mixed with any other.

Step one: pair the dimensions up. A head is 128 numbers. RoPE treats them as 64 adjacent pairs — (x₀, x₁), (x₂, x₃), and so on up to (x₁₂₆, x₁₂₇). Each pair is a point in a two-dimensional plane, and each plane is independent of all the others.

Step two: give every plane an angle. Plane i turns by θᵢ = position × ωᵢ, where the rates form a ladder ωᵢ = θbase−2i/dim with θbase = 2000 — the same geometric spread of fast and slow as the clock wall of §7, and for the same reason. Fast planes distinguish neighbouring positions; slow ones carry the coarse distance.

Step three: rotate each pair with its own 2 × 2 matrix.

Σ One plane of RoPE

[x₀′x₁′] = [cos θᵢ−sin θᵢsin θᵢcos θᵢ] [x₀x₁]

a rotation: it preserves the pair's length, changes only its angle, and touches no other plane

Sixty-four of those, one per plane, is the whole operation. Written as a single linear map it would be a 128 × 128 block-diagonal matrix — 64 little blocks down the diagonal and zeros everywhere else — and that matrix is never built. The code multiplies the pairs in place: it reshapes the head from (…, 128) to (…, 64, 2), applies the two rows of each 2 × 2 block, and reshapes back. No 16 384-element matrix, no matrix product, just four multiplications and two additions per pair.

Step four, FLUX.2's part: decide which axis owns which planes. A language model has one position, so all 64 planes would use it. FLUX.2 has four coordinates per token, and it splits the head between them: axes_dim = [32, 32, 32, 32] gives 32 numbers — 16 planes — to t, 32 to h, 32 to w and 32 to l. So planes 0–15 turn by the token's t-coordinate, planes 16–31 by its row, 32–47 by its column, 48–63 by its text position, each with its own 16-rung ladder of rates.

That is the whole of the four-axis trick: not a new kind of rotation, just an allocation of the 64 planes that were already there. And it explains the guard in __init__ — if the four allocations did not add up to exactly the head width, some plane would have no axis or two axes would fight over one, and the geometry would stop meaning anything.

💡 Why rotations, and not just adding a position vector

The older trick is to add a position embedding to each token. That changes the token's length and its direction, so what the network knows about the token and where it sits get entangled — and the attention score between two tokens depends on both positions separately, not on the distance between them. A rotation leaves the length untouched and has the property that matters: rotating a query by θ₁ and a key by θ₂ makes their dot product depend on θ₁ − θ₂ alone. Distance falls out of the arithmetic, which is what FIG 13 showed and what §8.1 promised.

The shapes, if you want them before Part 3: rope() takes one axis's positions (B, L) and its 32 dimensions and returns (B, L, 16, 2, 2) — sixteen 2 × 2 blocks, in float32; EmbedND concatenates the four axes into (B, 1, L, 64, 2, 2); apply_rope reshapes a head to (B, heads, L, 64, 1, 2) and multiplies. All three are walked through line by line in §16.4–§16.6.

A language model needs one position number per token. FLUX.2 needs four, because its tokens live in a 3-D volume of images stacked over a "time" axis, plus a separate index for text. Every token therefore arrives with a coordinate vector ids of shape (B, L, 4):

§ 9Time and guidance — how one float steers 32 billion weights

§6 built attention out of nothing and §8 built positions out of nothing, because every block in this file is wired around both. This section does the same for the third thing every block needs and the file never stops to define: how the network is told what to draw, and how noisy its input is. Nothing here is in model.py as a single named object — it is a mechanism spread over one function, one small class and one three-line class (§16.1, §16.3, §16.9) and consumed in all 56 blocks. Understand it once here and those three classes become trivial.

9.1 · One set of weights, fifty different jobs

Recall the loop from §1: generating one image means calling the same network many times — 50 times for FLUX.2-dev, 4 for the klein models — with a timestep t that walks down from 1 to 0. Those calls cannot want the same thing.

the call atwhat the input looks likewhat a useful output looks like
t = 0.98almost pure Gaussian noise — no objects, no layouta coarse global arrangement: where the subject is, how big, what the lighting does. Fine detail is meaningless here; there is nothing yet to refine.
t = 0.50a blurry but recognisable imageshape and texture decisions: edges placed, materials chosen
t = 0.05nearly the finished imagea small correction — sharpen here, fix a colour there. A coarse global decision now would destroy the picture.

So one fixed function has to behave like a different function at every step. There are only three ways to arrange that:

  1. Build one network per step. 50 copies of a 32-billion-parameter model. Absurd, and it could not generalise to a step count chosen at run time.
  2. Hand t to the network as another input token and let attention find it. Possible — but a single token among 16 896 is a weak, indirect signal, and every block would have to spend attention capacity re-discovering it.
  3. Keep one set of weights and let t re-tune them on the fly. No weight is ever changed; instead each layer's normalisation is shifted, scaled and gated by numbers derived from t. One network, fifty behaviours, almost no extra parameters.

FLUX.2 does the third. The mechanism is called adaptive layer normalisation (adaLN), and the rest of this section builds it from the ground up.

9.2 · Three ways to tell a network something

Before the mechanics, one distinction explains the whole design. A diffusion transformer has to be told several different things, and FLUX.2 tells them through different channels:

💡 The rule behind the split

Content goes into the sequence; settings go into the modulation. A prompt is content: different image regions need to look at different words, and only attention can route one token to another (§6). A timestep is a setting: it has to apply to every token in every layer at once, uniformly. Broadcasting one scalar through attention would be slow and lossy; handing it to each layer's normalisation reaches all 16 896 tokens in one multiplication. The guidance value is a setting for the same reason — it says "push harder towards the prompt", not "look at this".

9.3 · The other setting: what "guidance" actually is

The loop above passes the model four things — noisy latents, their position ids, the timestep, the text — and for some checkpoints a fifth: guidance. It is one number, and the file never explains it, so here it is. It matters twice: it is the second "setting" that §9 routes into the network, and it is a config field in §15 (use_guidance_embed).

The problem. A model trained to follow a prompt follows it politely. It produces something consistent with the words but hedged — washed out, under-committed, averaging over everything the prompt could have meant. Classifier-free guidance (Ho & Salimans, 2022 — §26) is the classic fix: run the network twice per step, once with the prompt and once with an empty one, and extrapolate past the conditional prediction.

Σ Classifier-free guidance, one step

v = v_uncond + w · (v_cond − v_uncond)

w = 1 → the plain conditional prediction · w > 1 → step further along "what the prompt changes" · w = 0 → ignore the prompt

The bracket is exactly what the prompt changes, so multiplying it by w > 1 amplifies only that. It works — and it doubles the cost: 100 network evaluations for a 50-step image.

What FLUX.2 does instead. use_guidance_embed says whether the model takes w as an input. Where it does, the value is fingerprinted and embedded exactly like the timestep and added to the same condition vector (§9.4), so a single pass approximates what the two-pass extrapolation would have produced — the model was trained to reproduce it, which is what "guidance distillation" means. The dev configuration sets use_guidance_embed=True and util.py drives it with guidance=4.0 over 50 steps. Both klein configurations set it to False: those networks have no guidance input at all, and util.py accordingly runs them with guidance=1.0 — no amplification — in 4 steps.

sampling.py still carries the two-pass version as its own entry point (denoise_cfg): it duplicates the batch, passes guidance=None to the model, and combines the two predictions outside the network. Same idea, no distilled input, twice the compute.

⚠ Do not confuse the two

A distilled guidance value — this file's guidance_in — is one scalar fed into one forward pass. True classifier-free guidance is two forward passes combined afterwards. Nothing in model.py ever does the second: the file only sees the scalar.

9.4 · From one float to 56 blocks' worth of dials

Now the pipeline that produces those dials. It has four stages, and each one exists because the previous one is not enough.

Stage 1 — the fingerprint. §7 built this one: t is multiplied by 1000 and read against 128 geometrically spaced frequencies, each reading taken twice — a cosine and a sine — which gives 256 numbers between −1 and 1. No parameters, nothing learned, smooth in t, and no two times in [0, 1] share a fingerprint. The fastest reading completes 159 cycles over a whole run and the slowest 1.7 % of one; that spread of scales is the entire trick, and it is what turns one float into something a 6144-wide matrix can actually work with.

Stage 2 — a fixed code becomes a learned meaning. The fingerprint is a deterministic function of t: no parameters, nothing learned. What it means to be at t = 0.62 is something the model has to discover, so the fingerprint goes through the smallest possible learned transform — two linear layers with a nonlinearity between them, 256 → 6144 → 6144 (§16.3). The nonlinearity is SiLU, silu(x) = x · σ(x) — a smooth, self-gated ramp that is near zero for very negative inputs and near x for positive ones. §16.2 turns that same function into a gate for the MLPs; here it is just the kink that lets two linear layers express more than one. Its output is the condition vector, vec, and it is the only form in which the timestep ever reaches the blocks.

Stage 3 — the guidance value takes the same road and is added. If the configuration has use_guidance_embed (§15, true for dev only — and §9.3 explains what the value means), the guidance scalar is fingerprinted and MLP'd through its own copy of the same class, and the two vectors are summed (L200–203):

Σ Two settings, one channel

vec = time_in(fingerprint(t)) + guidance_in(fingerprint(g))

(B, 6144) + (B, 6144) → (B, 6144)

Adding, rather than concatenating, means the two settings share every downstream matrix: there is one condition channel and the network learns to disentangle them. It also means guidance cannot be routed somewhere the timestep does not go — the two dials are fused from this point on.

Stage 4 — three matrices turn one vector into everybody's dials. vec is fed to three Modulation modules (§16.9). Each one applies SiLU and then a single bias-free linear layer, and splits the result into vectors of 6144:

module (built at L98–108)its matrixvectorswho consumes them
double_stream_modulation_img6144 → 36 8646the image stream of all 8 double blocks: (shift, scale, gate) for its attention, then (shift, scale, gate) for its MLP
double_stream_modulation_txt6144 → 36 8646the text stream of the same 8 blocks, same two triples
single_stream_modulation6144 → 18 4323all 48 single blocks — one triple, because after the merge there is one stream and one fused sub-layer

That is the naming trap in __init__: double=True does not mean "one triple per stream in a two-stream block". Each of the two double=True modules serves one stream and emits two triples — one for attention, one for the MLP. Six vectors, one stream.

◇ If you have never seen conditioning done this way

The one-sentence version: the timestep does not enter the network as data, it enters as a setting. A tiny side-network reads t and produces a handful of numbers per block; those numbers are multiplied and added into the activations at every normalisation point, so the same weights compute a different function at every step. Compare it with the two alternatives you may know from other models: a U-Net adds a time embedding to its feature maps (FiLM-style, the same family of idea), and a cross-attention model inserts the condition as extra keys and values (which is what FLUX.2 does for the prompt, not for the timestep).

That is the whole of this chapter's job: two settings in, one vector out. What fifteen dial vectors then do to 56 blocks — why they attach at the layer norms, what the third dial is for, and what sharing them costs — is §11, which picks up exactly here.

§ 10SiLUActivation — the soft switch

Between any two linear layers, a network needs something that is not linear, or the two layers collapse into one and the depth buys nothing. FLUX.2 uses exactly one such function, in two different jobs, and it has its own class in model.py. It is four lines long. This chapter is about the idea, which is older than the file and worth understanding on its own terms.

10.1 · The problem with a hard corner

The classic choice is ReLU: relu(x) = max(0, x). Negative inputs become exactly zero, positive ones pass through. It is cheap and it works, and it has one bad property: a unit whose input is negative has no gradient at all. During training, if a unit drifts into that region it stops learning — the famous "dead neuron" — and the capacity spent on it is lost. The corner at zero is also a discontinuity in the derivative, which makes the loss surface kinked in a way optimisers do not love.

The fix is to soften the corner. Instead of switching off abruptly, switch off gradually: use a smooth function that is near zero for very negative inputs and near one for very positive ones, and multiply the input by it. That smooth switch is the sigmoid σ(x) = 1 / (1 + e−x), and the result is SiLU — also called Swish:

Σ SiLU, in full

silu(x) = x · σ(x) = x / (1 + e−x)

smooth everywhere · no dead region · non-monotonic: it dips slightly negative before climbing

Read it as a sentence: a number, multiplied by its own smoothed on/off switch. Large positive inputs are essentially untouched (σ ≈ 1). Large negative inputs are essentially erased (σ ≈ 0) — but "essentially" is doing the work: they are multiplied by a tiny number rather than set to zero, so a gradient still flows and the unit can come back. And around x ≈ −1.28 the product dips to about −0.28 before recovering, which means the function is not simply "a soft ReLU": it can express a small negative response, something ReLU cannot do at all.

10.2 · Job one: an activation

The ordinary use. Anywhere the file needs a nonlinearity between two linear layers — the two-layer network that turns a timestep fingerprint into a condition vector (§16.3), and the projection that turns that vector into modulation dials (§16.9) — it puts SiLU in the middle. Two linear maps with nothing between them would compose into a single linear map, so all that depth would be wasted; one SiLU is what makes them two genuinely different transformations.

10.3 · Job two: a valve

The second use is more interesting, and it is why the class exists at all rather than being a call to torch.nn.functional.silu. Inside every one of the 56 blocks, the MLP projection is made twice as wide as it needs to be, and then split in half:

Σ SwiGLU — what the blocks' MLPs actually compute

mlp_out = silu(A) ⊙ B

A and B are the two halves of one wide projection · ⊙ is element-wise · one half decides how much of the other half gets through

Here SiLU is not shaping a signal, it is gating one. Half of the projection (A) is turned into a set of per-channel valves — mostly open, mostly shut, or anywhere between — and the other half (B) is the content that gets through them. The network learns, per token and per channel, how much of its own computation to let pass. This is the SwiGLU family of gated MLPs (Shazeer 2020, §26), and it is the same "multiply by a learned amount" idea that the modulation gate of §11.2 applies to whole sub-layers — one at channel level, one at block level.

It is also why the class is a module and not a function: the blocks hold it as self.mlp_act, so it appears in the module tree, and it is why the MLP widths in the configuration are not what they seem — a "3×" MLP ratio produces a projection that is split, so the effective hidden width is 3× while the matrix is 6× wide (§16.2 has the arithmetic).

◇ The one-line summary

SiLU is x times a smooth switch that depends on x itself. Used between two linear layers it makes depth meaningful; used against a second copy of the signal it becomes a per-channel valve. FLUX.2 does both, with the same four lines, in 58 places.

§ 11Modulation — how a vector steers 56 blocks

§9 ended with a vector: vec, 6 144 numbers that encode "how noisy is this input, and how hard should I push towards the prompt". This chapter is about what a vector like that can actually do to a network — the mechanism, the three dials, where they attach, and what the whole arrangement costs. There is no code here; the thirteen lines that implement it are §16.9.

11.1 · The idea, and the word for it

A neural network's behaviour is normally fixed once training stops: the weights are the behaviour. To make one network behave differently at different moments you have three options — change the weights (impossible at run time), change the input (limited: you can only tell it things through the data it already reads), or change the settings the computation runs under. The third is modulation, and the family of techniques goes by the name FiLM — feature-wise linear modulation — which means: multiply some activations by a number and add another, where both numbers come from somewhere else.

The name to know is adaptive layer normalisation, adaLN: FiLM applied at the normalisation inside each transformer sub-layer, with the condition vector as the source of the numbers. DiT (Peebles & Xie, 2022 — §26) made it the standard for diffusion transformers, and FLUX.2 uses it in every one of its 56 blocks plus the exit door.

11.2 · LayerNorm from zero — and why it is the place to inject

A layer norm acts on one token vector at a time — D numbers, independently of every other token, so it can never leak information between positions. It does two things:

Σ LayerNorm, in full

μ = mean(x) σ² = mean((x − μ)²) x̂ = (x − μ) / √(σ² + ε)

y = γ ⊙ x̂ + β

x is (L, D) · μ, σ², x̂, y are (L, D) · γ and β are (D,) — one number per channel, shared by all tokens · ⊙ is element-wise multiplication

The first line is normalisation: subtract the token's own mean, divide by its own standard deviation. After that, every token vector has mean 0 and unit variance, whatever it was before. Why bother? Because 56 blocks of matrix multiplication would otherwise let magnitudes drift — one block's output becomes the next block's input, and a weight matrix that happens to amplify by 1.1× compounds into something unmanageable over 56 layers. Normalising resets the scale at every step, so each block always sees an input in the range its weights were trained for.

The second line is the part that matters here. After x̂, the vector's scale and offset are fixed — the only freedom left in the whole operation is γ (a per-channel gain) and β (a per-channel offset). Those two are the knobs.

  • Let γ and β be learned constants and you have ordinary LayerNorm: the knobs are set once, at training time, and never move again.
  • Let γ and β be computed from something else — the timestep — and you have a layer whose behaviour changes from step to step while every weight in it stays frozen. Two knobs, turned 50 times, giving 50 different layers out of one.

That is the entire trick, and the file is built around it. PyTorch's nn.LayerNorm(D, elementwise_affine=False) deletes γ and β, leaving a module that only normalises. FLUX.2 uses exactly that setting in all 81 of its layer norms — the census in §14.1 — and supplies γ and β from the timestep instead. In the code they are spelled

Σ How the knobs are written in this file

x_mod = (1 + scale) ⊙ norm(x) + shift

L470 in the single block · L580 and L588 in the double block, before attention · L628 and L633, before the two MLPs

scale is playing γ's role and shift is playing β's. The 1 + is not decoration: with scale = 0 you get exactly the normalised signal, so "nothing special is happening" is the default state and the network only has to learn a deviation from it. It is the same idea as a residual connection, applied to the modulation itself — and it is why the modulation can be shared by 56 blocks without every block being forced into the same extreme behaviour.

11.3 · Shift, scale, gate: three dials per sub-layer

Shift and scale re-tune what a block sees. DiT (Peebles & Xie, 2022 — see §26) added a third dial, and FLUX.2 keeps it: a gate that multiplies the sub-layer's output before it is added back into the residual stream.

◇ The residual stream, in one paragraph

Every token owns a vector of 6144 numbers that is carried through the whole network, and each block adds to it instead of replacing it: x ← x + block(x). That running vector is the "residual stream" — the token's current understanding of itself, which starts as a projected patch (§4) and ends as a velocity (§1). Two things follow, and both matter below. A block cannot destroy what earlier blocks decided, only amend it — which is what makes 56 layers trainable at all. And a block that contributes nothing is a perfectly valid state: set its output to zero and the stream passes through unchanged. That is why a gate is worth having — next — and why the merged stream in §20.2 can be handed to 48 further blocks without any rewiring.

Σ One adaLN sub-layer

x ← x + gate ⊙ sublayer( (1 + scale) ⊙ norm(x) + shift )

shift, scale, gate are all (B, 1, D) — one value per channel, broadcast over all L tokens

Think of the gate as a volume knob on the block's contribution. gate = 0 and the block is a no-op — the stream passes through untouched, however excited its internals got. gate = 1 and the block's full output lands in the stream. In between, the block contributes partially. Shift and scale cannot do that: they change the input, so the block always runs, and its output always arrives. The gate is what lets the same 56 blocks do coarse global work at t = 0.98 and delicate local work at t = 0.05 — different layers can be turned up or down per step.

The second consequence is the one that generates real code. A broadcast dial cannot distinguish one token from another — it is (B, 1, 6144), the same for every position. But reference tokens have to be conditioned at t = 0 while the canvas sits at t = 0.62 (§22.1 explains why). One shared triple cannot say that. So forward_kv_extract runs the modulation twice: once with the real timestep, and once with a timestep pinned to 0.0 for the references (L198, L206–211).

Two runs produce two sets of dials, but every block receives one. So the two sets are spliced into a per-token tensor whose first rows come from the reference run and whose remaining rows come from the real one — and that splice is the entire reason _blend_mod_triple, _blend_double_mods and _blend_single_mods (§21) exist. Shared modulation is cheap; this is the bill.

§ 12The KV cache — paying for a computation once

A generation run calls the same network dozens of times, and most of what it computes on any given call has nothing to do with the step it is on. This chapter is about noticing that, about the one part of FLUX.2's input that genuinely never changes, and about the three conditions that make reusing it exact rather than an approximation. No code — the three forward passes that implement it are §20 and §22.

12.1 · The waste

Look at what one step of a reference-guided run has to process. At 1024² with four reference images the sequence is 20 992 rows: 512 of text, 16 384 of reference, 4 096 of canvas (§5). Every row goes through both kinds of block, and inside each block every row is projected into queries, keys and values by three large matrices.

Now ask which of those rows change between step 1 and step 2:

rowscountdo they change?so what is recomputed for nothing?
canvas4 096yes — every step, that is the point of the walknothing: this work has to be done
text512no — the prompt is fixed, but the tokens are conditioned at the current t, so their values movea little; and they are only 2 % of the sequence anyway
references16 384no, and provably so — same latents, same fixed timestep, sealed off from the canvas79 % of the sequence, recomputed identically, 49 times out of 50

That last row is the whole opportunity. The reference tokens are the same numbers, in the same positions, under the same conditioning, at every step of the run — so their keys and values are the same numbers too. Computing them again is not a different answer arrived at twice; it is the same answer arrived at twice, forty-nine times over.

12.2 · What gets cached, exactly

Not the reference tokens themselves — they were never going anywhere. What gets cached is the two things attention actually reads from them:

Σ What a cache entry is

per block: k_ref and v_ref — the reference rows' keys and values

56 blocks × 2 tensors × 16 384 rows × 6 144 numbers

that is the whole cache. No queries, no attention outputs, no activations.

  • Why keys and values? Because those are the only two roles a token can play for someone else. A query is how a token asks; a key is how it is found; a value is what it contributes once found (§6). The reference tokens are never asking anything in the cached path — they produce no output rows — so their queries are never needed. Their keys and values are needed by every canvas token at every step, and those are exactly the two tensors that get stored.
  • Why per block? Each block has its own key and value matrices, so each block's version of the reference tokens is different. There is no such thing as "the" reference key — there are 56 of them, one per block, and the cache holds all 56 pairs.
  • Why is it expensive anyway? 56 × 2 × 16 384 × 6 144 numbers is 11.3 billion values. At two bytes each that is 22.55 GB — comparable to the model's own weights, for one image's worth of references. The cache trades memory for compute, and it is not a small trade (§22.2 does the arithmetic for all three checkpoints).

12.3 · Why this is exact, and not an approximation

Most caching in machine learning trades accuracy for speed: you reuse something that is close enough. This one does not, and the difference matters, because it is the only reason the trick can be used at all. Three conditions have to hold simultaneously.

⚠ The other reference path does not satisfy these, and is not the same model

There are two ways to drive references in this codebase, and only one of them is cacheable. The plain path concatenates the references onto the canvas and runs them with it: they attend to the noisy image, they are conditioned at the current timestep, and they are recomputed every step. Different mathematics, different pictures — which is why the cached variant ships as its own checkpoint (flux.2-klein-9b-kv) rather than as a flag on the ordinary one. A cache is only free when the thing you are caching was never going to change; here that is a design decision made in three places at once, and §22.1 lists them.

12.4 · What it buys, and why not more

The token arithmetic looks spectacular: dropping 16 384 of 20 992 rows should make a step about twelve times cheaper. The measured speedup is 2.66×. Both numbers are right, and the gap is worth understanding, because it is the difference between counting tokens and counting work.

what the cache removeswhat it does not removewhy
projecting 16 384 reference rows through every block's key, value and query matricesthe canvas and text projectionsthey change every step, by definition

So the honest summary is: the cache deletes the reference tokens' projections and their output rows, and keeps everything about how the canvas reads them. Where references dominate the sequence that is a large win — 2.66× at 512² with four of them — and where they do not it is a small one: at 1440² the canvas has grown to 8 100 rows, the references are 67 % of the sequence instead of 94 %, and the measured win falls to 1.85×. §22.3 has all four measurements and the arithmetic behind each.

💡 The general lesson

A KV cache is not a trick specific to image models or to FLUX.2 — it is the same observation that makes autoregressive language models usable: some tokens' keys and values do not change, so compute them once. In a language model the unchanging tokens are everything generated so far. Here they are the reference images. The shape of the saving is the same in both cases, and so is the shape of the cost: a store proportional to the number of cached tokens times the number of layers, read on every single step.

§ 14What FLUX.2 actually is

You ask for "a red fox in snow at dusk". FLUX.2 does not draw the fox. It starts from pure static and, over 50 small corrections, pushes that static until it becomes a fox. model.py is the thing that decides which way to push.

FLUX.2, released by Black Forest Labs in November 2025, is a latent flow-matching image model. Three separate networks cooperate:

  1. A vision-language model (Mistral-Small-3.2, 24B parameters) that reads your prompt and produces a list of meaning-vectors. This is the part with world knowledge — it knows what a fox looks like, what "dusk" implies about lighting, and how to spell words you ask it to render.
  2. A variational autoencoder (VAE) that shrinks images by 16× in each spatial direction. Instead of pushing around a million pixels, the model pushes around four thousand compact latent tokens. This is what makes the whole thing computationally possible.
  3. The rectified-flow transformer — this file — which repeatedly looks at the half-finished image plus the meaning-vectors and answers one question: "what should change, and by how much?"

Zero nn.Dropout modules. At 32B parameters trained on a very large dataset, regularisation by dropout is unnecessary — the model is far from overfitting. Inference and training graphs are therefore identical, which also makes the code simpler to read.

◇ Beginner · why is theta only 2000?

Think of the 16 planes of one axis as the wheels of an odometer (§8.2). The fastest wheel turns once every 2π positions — it is what tells position 41 from position 42. The slowest wheel turns once every 2π·θ positions — it is what tells position 4 from position 4000, because the fast wheels have gone round and round and look identical again. Language models use θ = 10 000 or more because their positions run into the hundreds of thousands: they need a wheel slow enough not to wrap inside the context.

FLUX.2's coordinates are tiny by comparison — grid indices under ~200, text indices under 512, and a t axis that only ever reaches about 100 — so its slowest plane (period 2π·2000 ≈ 12 566 positions, FIG 16) is already far slower than the longest distance it will ever be asked about. inference A smaller base than 10 000 therefore costs nothing here and keeps the rest of the ladder in the range of distances the model actually needs to resolve; model.py simply states theta: int = 2000 (L19) without saying why.

16.1 · timestep_embedding(t, dim, max_period, time_factor) — L710

The model needs to know how noisy its input is. But a single float like 0.87 is a terrible input for a neural network: one number cannot be meaningfully multiplied by a 6144-column weight matrix in a way that distinguishes 0.87 from 0.86. The standard fix, inherited from the original diffusion paper and from Transformers' positional encoding, is to expand the scalar into a bundle of sines and cosines at many different frequencies.

16.5 · EmbedND — L694

Every token that enters FLUX.2 carries a small address: four numbers, one per position axis (§8). EmbedND is the machine that turns those addresses into something attention can actually use — a stack of rotation matrices, one per rotation plane of the head. It owns no parameters at all: no weights, no tables, just trigonometry, recomputed from scratch on every call.

What goes in

One tensor, ids, of shape (B, L, 4): a batch of L tokens, each with its four integer coordinates. (sampling.py builds them with torch.cartesian_prod over torch.arange, so they arrive as int64; rope multiplies them by a float32 frequency ladder, which is where they become angles.) Concretely, a row looks like this:

tokenthwlwhy
a canvas token at row 17, column 42017420the image being drawn lives at t = 0; text slot unused
the same pixel of reference image #33017420references sit ten t-units apart: 10, 20, 30…
the 6th word of the prompt0005text has no pixels: t, h, w are dummies, l sweeps the sentence

The constructor also takes three settings: dim = 128 (the head width — stored, and then never used again; the real budget comes from axes_dim), theta = 2000 (the frequency base), and axes_dim = [32, 32, 32, 32] — how many of the 128 head dimensions each axis owns.

What happens inside — four slices, four ropes, one glue

Step 1 — slice off one column. ids[..., i] takes axis i's coordinate for every token at once: a (B, L) tensor of plain positions. For i = 1 that is the list of all row numbers; for i = 3 the list of word indices.

Step 2 — rope that column. Each slice is handed to rope (§16.4) together with that axis's dimension budget, axes_dim[i] = 32. rope pairs those 32 dimensions into 16 rotation planes and writes one 2×2 rotation matrix per plane per token — the matrix from §8.1, with angle position × ω of that plane. Output per axis: (B, L, 16, 2, 2) = batch × token × plane × 2×2 matrix.

Step 3 — glue the four bundles together. torch.cat([...], dim=-3) stacks the four bundles of planes end-to-end along the plane axis: 16 + 16 + 16 + 16 = 64 planes, giving (B, L, 64, 2, 2). Why dim=-3? Count axes from the right: −1 is the matrix column, −2 the matrix row, −3 the plane. Concatenating at −3 leaves every 2×2 matrix untouched and simply lines the planes up in axis order — t's 16 planes first, then h's, then w's, then l's. That order is a contract: plane j of this output is exactly the rotation that apply_rope will apply to dimensions (2j, 2j+1) of q and k, which is precisely the dim-split drawn in FIG 16.

Step 4 — make room for heads. unsqueeze(1) inserts a size-1 axis at position 1: (B, 1, L, 64, 2, 2). All 48 heads of a layer share the same rotations, so a size-1 axis lets one computed copy broadcast across every head for free during apply_rope — the rotations are computed once per token, not once per token per head.

💡 Why write a class with no forward?

Honest answer: it groups the four attention parameters under one name so that block.img_attn.qkv.weight reads clearly and so checkpoint keys stay tidy, while letting the block control exactly how and when each piece is used. FLUX.2's blocks need to interleave attention with modulation, RoPE and the reference routing of §17, so a rigid forward(x) → x would not fit anyway. It is a pragmatic choice, and once you know it the file stops being confusing: whenever you see self.X_attn. followed by a member name, you are looking at parameter access, not a call.

§17causal_attn_fn — the attention router · L758

Fifty-eight lines that decide, for every query in the sequence, which keys it is allowed to read. Despite its name there is nothing autoregressive here — the "causality" is of a different, more interesting kind.

⚠ Gotcha · the name lies

In an LLM, "causal attention" means token i may not see tokens after it — the triangular mask that makes text generation possible. causal_attn_fn contains no triangular mask at all: all three of its scaled_dot_product_attention calls pass is_causal=False. What it implements instead is a block-diagonal isolation rule: reference tokens are causally cut off from the rest of the sequence — they may read each other, and nobody's updates may leak into them. That single property is what makes the KV cache of §22 mathematically exact. Read the name as "references are sealed", not as "left-to-right".

§19DoubleStreamBlock · L524

The first eight blocks of the network are different. Text and image keep separate weights — separate norms, separate projections, separate MLPs — and meet only inside the attention, where their queries and keys are concatenated so each modality can read the other. This is the MM-DiT idea from Stable Diffusion 3, and it is what lets a word-vector and a pixel-vector, which live in completely different statistical worlds, share one attention operation without one corrupting the other.

sampling.py can drive references two ways, and they are not the same computation. denoise concatenates the references onto the canvas and calls forward(), which hard-codes num_ref_tokens=0 (L150, L162): nothing is isolated, the references attend to the noisy canvas, they are conditioned at the current timestep, and they are recomputed on every step. denoise_cached calls forward_kv_extract once and forward_kv_cached thereafter, where the references are sealed off (§17.2) and conditioned at t = 0.0. Different mathematics ⇒ different images, which is why the cached variant ships as its own checkpoint (flux.2-klein-9b-kv) rather than as a flag on the normal one.

Token order is not what distinguishes them. Positions travel with their tokens through RoPE, so [img, ref] and [ref, img] describe the same computation up to a permutation of rows. What matters is whether the references are isolated and frozen.

So: the cache pays off precisely when you are doing reference-guided work at modest resolution, and it pays off by a factor of two-to-three, not by the factor of twelve the token count suggests.

At the last step t_prev = 0, landing exactly on the clean latent, which the autoencoder then decodes into pixels. There is no noise injected anywhere: this is an ordinary differential equation being integrated, not a stochastic process.

23.1 · Which timesteps? A deterministic, shifted ladder

The step times are not evenly spaced — but they are not random either. get_schedule(num_steps, image_seq_len) (sampling.py L244–248) builds a uniform ladder torch.linspace(1, 0, num_steps + 1) and warps every rung through the shift function of §1.3, t′ = eμ / (eμ + (1/t − 1)σ) with σ = 1. Same run in, same run out — there is no sampling and no seed.

μ comes from compute_empirical_mu (sampling.py L251–266) and depends on two things. Above 4300 image tokens it is a straight line in the token count, μ = 0.00016927·L + 0.45666666. At or below 4300 tokens it interpolates between two fitted lines — one calibrated for a 10-step run, one for a 200-step run — so the step count matters too: fewer steps ⇒ larger μ ⇒ the few steps you have are pushed harder into the noisy end. ⚠ Gotcha · "logit-normal" is a training word, not an inference word

The SD3 paper samples its training timesteps from a logit-normal distribution, and that phrase is often reused for inference schedules. Nothing here is sampled or normal-distributed: the inference schedule is a fixed monotone warp of a uniform ladder, and the warp's μ is fitted empirically (per compute_empirical_mu's own name) rather than drawn. The two ideas are related — the shift concentrates steps where training concentrated probability — but they are not the same statement.

FLOPs = 2 × (MACs in the blocks + MACs in the attention)
